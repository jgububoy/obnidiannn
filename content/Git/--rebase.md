# --rebase

`git rebase` არის **git**-ის მექანიზმი, რომლის დროსაც შენ მიერ გაკეთებული კომიტების მიმდევრობა იხსნება, შტო იდეურად სინქრონიზდება უახლეს ბაზასთან და შენი კომიტები სათითაოდ იდება ახალი ბაზის თავზე, რაც ქმნის სუფთა, ხაზოვან ისტორიას.

[obsidian git <- -> git obsidian  ( --rebase )](obsidian%20git%20<-%20->%20git%20obsidian%20%20(%20--rebase%20).md) 

**როგორ მუშაობს რებეისი?**

* **დროებითი შენახვა:** როცა აკეთებ `git pull --rebase`-ს, გიტი შენს მიერ ლოკალურად დაწერილ, სერვერზე ჯერ არგაგზავნილ კომიტებს დროებით „გვერდზე დებს“.
* **ბაზის განახლება:** შტოს საწყის წერტილს (Base) წევს სერვერზე არსებულ რეალურ, უახლეს მდგომარეობამდე.
* **თანმიმდევრული აწყობა (Re-applying):** შენს მიერ შექმნილ კომიტებს სათითაოდ, რიგრიგობით ადებს ახალი ბაზის თავზე იმ თანმიმდევრობით, რა თანმიმდევრობითაც გქონდა დაწერილი.

**პლიუსები**

* **სუფთა და ხაზოვანი ისტორია:** არ იქმნება ზედმეტი „Merge branch...“ ტიპის კვანძები. `git log` გამოიყურება როგორც ერთი სწორი ხაზი, სადაც ზუსტად ჩანს შენი მუშაობის ეტაპები.
* **ადვილად მართვადი პროექტი:** ერთ შტოზე მუშაობისას არ იბნევა ისტორია და ყოველთვის ზუსტად იცი, რა მიყოლებით წერდი კოდს.

**მინუსები და რისკები**

* **ისტორიის გადაწერა (History Rewriting):** რებეისი ფიზიკურად ცვლის კომიტების უნიკალურ იდენტიფიკატორებს (hashes). თუ კოდი უკვე გაგზავნილია (`push`) და სხვასთან ერთადაც მუშაობ იმავე შტოზე, ამან შეიძლება სერიოზული არეულობა გამოიწვიოს. შენს შემთხვევაში (როცა ერთადერთი მომხმარებელი ხარ, უბრალოდ სხვადასხვა კომპიუტერიდან ჯდები) ეს პრობლემა არ არის, მთავარია ყოველთვის გამოიყენო `--rebase`, როცა სერვერსა და შენს კომპიუტერს შორის სხვაობა გაჩნდება.
* **კონფლიქტების ეტაპობრივი გავლა:** თუ რებეისის პროცესში რამდენიმე კომიტს შორის არის კოდის გადაფარვა, შესაძლოა კონფლიქტის გასწორება მოგიწიოს არა ერთხელ, არამედ თითოეულ „გადაბრუნებულ“ კომიტზე ცალ-ცალკე (`git rebase --continue` პროცედურის გავლით).
