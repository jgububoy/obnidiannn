1. `git status `- ფაილები რა მდგომარეობაშია ( **untracked, staged, commited** ) 
2. `git add` - - -  **staged**  ზონაში გადაყვანა.
3. `git add .` - - - *ამზადებს* **ყველა** **შეცვლილ** და **ახალ ფაილს** მიმდინარე დირექტორიასა და მის ქვეპაპკებში,  შემდეგ **კომიტში შესატანად**.
4. `git commit  -m "კომნტარი" `  -  ყველა  დასაქომითებლად გამზადებული( **მწვანე ზონაში მყოფი - staged** ) ფაილები დაქომითდება.

არსებული ფაილის **დარედაქტირების** შემთხვევაში, გადადის **untracked** სტატუსში, ოღონდ როგორც  ***untracked/modifited*** .
და შემდეგ  ისევ  _**git add**_ -ით  გადაგვაქვს **_staged_** -ში  და  მერე ვაქომითებთ **git commit**..

```bash
git add file1 file2 ...
git add .  - - - არსებულ საქაღალდეში ყველას დამატება ( untracked-დან staged-ში )
git add *.py  - - - პითონის გაფართოებებიანი ფაილების დამატება
git add folder/*.py  - - - კონკრეტული საქაღალდიდან პითონის ფაილებიანის დამატება
git add folder/  - - - კონკრეტული საქაღალდიდან ყველა ფაილებიანის დამატება
git add "*.py"  - - -  მთელ პროექტში არშებული პითონის ფაილების დამატება
```


4. `git log` - - კომიტების **ისტორიების/მდგომარეობის** ნახვა. (   [git log -ის გაშვების ჩეპეები:](Git%20Log%20-ის%20პრობლემების%20მოგვარება.md)  )

## GIT N5. "ქომიტების" *გაუქმება/წაშლა* ( git reset )

> P.S. შტოებს უძახიან **master** და **main შტოები** , რაც ერთიდაიგივეა.

შესაძლებელია უკან ისტორიაში დაბრუნება, ასევე შეიძლება არასწორმა commit-მა დაგაკარგიოს ინფორმაცია. ამიტომ **ძალზედ საყურადღებოა.** 

**syntax:** - - - `git reset [--soft ; --mixed ; --hard] [commited_ID ; HEAD^^]`

![|389x160](_attachments/9378102e63a3b52ac7e59b8926d43811.png)
.
- **HEAD** - - - გვიჩვენებს რომელ commit-ზე ვდგავართ ახლა. როგორც წესი ბოლო აქტუაური ქომითია ხოლმე. ზოგადად ამ head-ის გადაადგილება შეიძლება. 
- `... HEAD^` - - - ეს ნიშანი ` ^ ` გულისხმოს  ისტორიაში ერთ ნაბიჟით უკან გადავალთ.  თუ `^^` , მაშინ **2** ნაბიჯით.
- `... HEAD~3` - - -  ასეც ` ~ ` შეიძლება **3** ნაბიჯით უკან გადასვლა.
- ასევე შესაძლებელია _ქომითის_ კონკრეტული   _**ჰეში(ID)**_   მივუთითოთ და იმაზე გადავალთ.

### git reset -ის 3 რეჟიმი:  soft ; mixed ; hard 

>  **untracked** -ში რაც არის **ვერცერთი ვერ იშლება** reset ბრძანებით --- მხოლოდ **clean**-ით !!!!
>  იმ ლოგიკით რომ ეს გარემო თავისი არსით ნიშნავს, **არ არის აყვანილი აღრიცხვაზე**, ანუ git-ისგან კონტროლს არ ექვემდებარება. თუ მაინც reset-ით გვინდა წაშლა,  **modifited** , **untracked/modifited** ან **staged** გარემოში უნდა გადავიყვანოთ(ანუ **git-ის კონტროლ ქვეშ**) და მერე შეიძლება ამოშლა.


- `git reset --soft HEAD^` 
	- **( commit   ==>  staged )**
	- **( staged ==> staged )**
	- **( untracked ==> untracked )**
- `git reset --mixed HEAD^` ან `git reset HEAD^`
	- **( commit , stage   ==>  untracked/modifited )**
	- **( untracked ==> untracked )**
- `git reset --hard HEAD^`
	- **( commit, stage      ==>  delate )**
	- **( untracked ==> untracked )**
- `git reset `
	- **(  stage    ==>   untracked )**

#### 1. **--soft**

```bash
git reset --soft HEAD^
```

გადავიდეთ იმდენით რამდენიც არის მითითებული **HEAD**-ით. 
სანამ გადავიდოდით, ბოლო commit-ზე რაც  **დაქომიტებული** იყო, ყველაფერი გადავა _**staged**_ გარემოში და თავად **ფაილები არ წაშლება**.   
ხოლო ბოლო commit-ის დროც რაც  **Untracked** გარემოში იყო ,  ისედაც **untracked** -ში დარჩება. 

  - **( commit   ==>  staged )**
  - **( staged ==> staged )**
  - **( untracked ==> untracked )**

#### 2. **--mixed** ( default - ად ეს აყენია )

```bash
 git reset --mixed HEAD^
 იგივეა: 
 git reset HEAD^
```

`--mixed ` გასაღების მითითებით მოხდება ისევე HEAD-ით უკან გადასვლა და ფაილები იგივე ლოგიკით ოღონდ **untracked** სივრცეში.  
( **default**-ად ასეა, შეგიძლიად არ დაწერო ხოლმე და **იგივეა** :  ` git reset HEAD^ `  )
 ფაილები  აქაც **არ წაიშლება.** 

   (შეიძლება არ დაიწეროს,     დეფაულთზეა  )   - დარჩენილი ფაილები  არ წაიშლება და გადავა_**untracked/modifited**_   სივრცეში.    

  -  **( commit , stage   ==>  untracked/modifited )**
  - **( untracked ==> untracked )**
  
#### 3. **--hard**

```bash
  git reset --hard HEAD^
```

  ​არცერთ სტატუსში არ გადაანაცვლებს ფაილებს.

  **საყურადღებოოოოააააა!!!!!**
 > იშლება ყველაფერი ( **დაქომითბული**   და   **stage**  -ში   არსებული ფაილებიც ), გარდა    **untrackted**  ფაილებისა.

## GIT N6. "ქომიტების" ისტორიასთან მუშაობა ( *git checkout* )

[GIT N6. "ქომიტების" ისტორიასთან მუშაობა (git checkout) - YouTube](https://www.youtube.com/watch?v=BmBaoxaFgVM&list=PLbZtgfvYfOp3l7dZAnFVfY-bMC6dhP-vO&index=7)

>[!important] მუშაობის ალგრითმი:   
> 1. `git checkout COMMIT_ID`   ---  **master** შტოდან გადავდივართ რომელიმე კონკრეტულ **კომიტში** ფაილების დასათვალიერებლად
> 2. `git checkout master`   ---  ვბრუნდები **master**   შტოში
> 3. `git checkout COMMIT_ID -- file.txt`   ---  კოკრეტული ქომითიდან გადმოგვაქვს კანკრეტული ფაილი ან ფაილები **master** შტოში,   რომელიც არის **stage** გარემოში

###  1. წინა ქომითებში გადასვლა     და   *დათვალიერება*:

**ქომიტებს** შორის გაადგილება, მათი **განადგურების გარეშე**. გარდა ამისა შესაძლებებლია ფაილების სხვადასხვა **ვერსიებთან** და **შტოებთან** მუშაობაც.

**git checkout** :
1. _**commit**_-ებს შორის გადდადგილება
2. კონკრეტული ფაილების ვერსიების ამორჩევა
3. _**შტოებთან მუშაობა**_ - **(**ამას მოგვიანებით უფრო ვრცლად განვიხილავთ**)**

## GIT N7. "git commit" ბრძანების შესაძლებლობები. "*git clean*" ბრძანება

### commit-ის სპეციალური გასაღებები/ალმები : 

მხოლოდ  **untracked/modifited**(დარედაქტებული) და **stage** ფაილები **პირდაპირ ქომითდება** და არა **untracked** ფაილები. ( **გამოტოვო** `git add .`)

```bash
git commit -a -m  "edit file"
```

`-a `- - - (**all**) ყველა modifited ფაილის დაკომიტება
`-m `- - - კომენტარს/სახელს რომ ვუწერთ (ახლა "**edit file**") მაგისთვისაა

**ბოლო  ქომითების  კომენტერების  რედაქტირება :**

```bash
git commit --amend -m "new coment"
```

`--amend `- - - ჩაანაცვლებს ბოლო კომენტარს კომიტზე. 


#### **unstracked**   ფაილების  წაშლა:

**reset**-ით **untracked** ***ფაილებს ვერ ვშლით***, ვერ ვეხებით. 
**untracked   git**  -თვის ნიშნავს უკონტროლოს.   ამისთვის არსებობს   **clean** თავისი გასაღებებით.

```bash
git clean -n     - - -    -n გასაღბი გვაჩვენებს untracted ფაილების სიას, რომლის წაშლას აპირებს:

Would remove file3   - - - ბრძანება გამოაქვს. "ეს ფაილია ასეთი და გინდა წაშალოო?"  
                                                         ( ანუ ჯერ არ წაუშლია)  
```

```bash
git clean -f      - - -  -f(force) ყოველგვარი გაფრთხილების გარეშე შლის ყველა untracked ფაილებს.

Removing file3    - - -  გამოიტანა შეტყობინება რა ფაილებიc წაშალა.
``` 

```bash
git clean -f file.name    - - -   untraked ფაილებიდან კონკრეტულის  წაშლა
Removing file.name
```

> **განშტოება** - - -აზრი ისაა რომ ან შენ ან გუნდი მუშოაბთ, ტესტავთ აკომიტებთ... მთავარია მუშაობს ყველაფერი  გატესტილია და მერე ამას გადაიყვან **master** - სტაბილური ვერსიების შტოში. 

![](_attachments/3eeb56330b8163c28a0ea016a860b74c.png)

```bash
git branch             - ყველა შტოს სია რაც გვაქვს. და რომელზეც დგახარ იქვე მინიშნებულია.
git branch <name>      - ახალი name შტოს დამატება
git branch -d <name>   - name სახელის შტოს წაშლა. (სხვაზე უნდა იდგე)
git checkout <name>    - name შტოზე გადასვლა. როგორც commit-ების შემთხვევაში გადადიოდი/გადმოდიოდი
git checkout -b <name> - თან შექმნა და თან გადასვლა ახალ შტოზე.

git merge <name>       - დამატებითი(პირობითად feature იყო) შტოდან ცვლილებების გადმოტანა მთავარ
                       შტოში.მაგრამ უნდა ვიდგეთ მთავარ შტოზე. 
                       ანუ ვეუბნებით გადმოიტანოს name შტოდან ინფორმაცია. 
```

**მაგალით რაც გავაკეთე ამ მონაცემებით:**
1. შევქმენეი ფაილი **file.txt** და დავაკომიტე როგორც წესია **master  შტოში**. 
2. დავამატე **future შტო** და ამ შტოში მყოფმა გავხსენი იგივე file.txt
	1. ამ ფაილში ცვლილებები შევიტანე (რაღაცა წავშალე, რაღაცა დავამატე.) 
	2. ესეც ჩვეულებრივ დავაკომითე. და **future შტოში** მყოფს  **log** -ში მაქვს : 
	3. ![333x221](_attachments/9d9a2bf0a599f82113abe9c456d48d1b.png)
	4. ანუ დაფუშული , main-ში რაც იყო ის უკვე უფრო ძველია. ნუ ეს ცნობისათვის. 
	5. მაგრამ მთავარი ნიუანსი ახლა იქნება , ისევ **master შტოში** რომ გადავალთ.
3. გადმოვედით checkout-ით master შტოში...
4. ახლა აქ რომ გავხსნი იგივრ **file.txt** -ს, შეტანილი ცვლილებები არ გამომიჩდება, რადგანაც ის ცვლილებები სხვა შტოზე ყოფნისას შევიტანე. 
5. master შტოში გადმოსატანად იმ ცვლილებისა უნდა დავმერჯო: 
6. `git merge future` - - - **future** შტოდან გადმოიტანე ცვლილებებითქო.  და აქ იჩითება ახალი **fast-forward**. 
7. ასევე რომ დავმერჯე, **master**-ში გადმოვიტალე. ლოგებშ შემდეგი სურათია
	1. ![|406x239](_attachments/e4df09a7f0effc86c31aacb34f3c9d3a.png)
	2. **main**(იგივე **master**) და **future შტოები** ერთწერტილში მოექცა, დასინქრონებულია,  გათანაბრდა, გაუსწორდა ერთმანეთს, როვნადაა.
8.

## GIT N11. "git pull" ბრძანების მექანიზმი ( *git fetch , merge* )

[GIT N11. "git pull" ბრძანების მექანიზმი (git fetch, merge) - YouTube](https://www.youtube.com/watch?v=JOHLQudafXw&list=PLbZtgfvYfOp3l7dZAnFVfY-bMC6dhP-vO&index=11) 

- `git pull`- - - (**ჩამოქაჩვა**) ( გულისხმობს `fetch`-ს და `merge`-ს ერთად ), **ქაჩავს** განახლებებს დისტანციური რეპოზიტორიიდან და ავტომატურად აერთიანებს(**მერჯავს**) მათ თქვენს მიმდინარე ლოკალურ განშტოებაში.
* `git fetch`- - - **ჩამოტვირთავს** ისტორიასა და განახლებებს დისტანციური სერვერიდან და მხოლოდ **ანახლებს origin/master** შტოს.  
	* თქვენს ლოკალურ ფაილებში ცვლილების ან **შერწყმის გარეშე**( ***დამერჯვის გარეშე*** ). 

![](_attachments/1d07256dc1790cd4cd7c4ae735bc2a0a.png)

- `-r` ნიშნავს **remotes**-ს
- **რას აკეთებს:**  - -- ჩამოთვლის ყველა იმ ბრენჩს, რომლებიც ინახება შორეულ სერვერზე (მაგ: `origin/main`, `origin/dev`), თუმცა ეს არის ბოლო ცნობილი მდგომარეობა შენს კომპიუტერში არსებული ქეშიდან.

- `git branch` - - -  აჩვენებს მხოლოდ შენს ადგილობრივ (local) ბრენჩებს.
- `git branch -r` - - -  აჩვენებს მხოლოდ დისტანციურ ბრენჩებს.
- `git branch -a` - - -  აჩვენებს როგორც ადგილობრივ, ისე დისტანციურ ბრენჩებს ერთად.
